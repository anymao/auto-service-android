# Demo 场景验收面板设计

## 目标

将 `app` 从仅输出 Logcat 的基础示例升级为一个可直接观察结果的单页验收面板。它面向库的使用者演示运行时 API，并以可回归的单元测试锁定场景语义。

## 范围

页面在启动时运行全部场景，并提供“重新执行”入口。每个场景显示通过或失败、简短结果和必要的诊断信息。单个场景失败不得阻止其余场景执行。

覆盖的运行时场景：

1. 按接口加载 `Runnable`，并展示实现类及其顺序。
2. 按接口加载 `Callable`，验证一个实现可注册到多个接口。
3. 按 alias 加载 `Runnable`，验证只得到匹配的实现。
4. 读取加载结果的首尾项，展示 priority 排序的观察结果。
5. 在同一个 loader 结果上重复遍历，展示实例是否复用；单例实现的语义由结果文字说明。
6. 并发加载并汇总成功次数，展示调用不会因并发而失败。
7. 调用 `diagnose()`，在 Debug 展示候选及状态；在非 debuggable 变体将诊断不可用标为预期状态而非失败。

不纳入页面的构建期能力：项目模块与 AAR 扫描、排除/require DSL、重复类报错、缓存和发布配置。这些由 Plugin TestKit 继续覆盖，避免把构建期验收伪装成运行时页面能力。

## 结构

新增一个不依赖 Android View 的场景执行器，输入当前变体是否可输出诊断，输出稳定的场景结果列表。场景结果至少包含标题、是否通过、摘要和详情。`MainActivity` 仅负责生命周期、点击事件和把结果渲染到 XML 页面。

运行时执行流程：

```text
重新执行/启动
  -> DemoScenarioRunner.runAll()
  -> ServiceLoader 的 load / diagnose API
  -> List<DemoScenarioResult>
  -> MainActivity 渲染总状态和结果行
```

没有生成注册表、空结果或调用异常时，执行器将异常转换为该场景的失败详情；不会让 Activity 崩溃。Release 中的空诊断报告按库的设计解释为成功的隔离行为。

## 测试策略

先为场景执行器编写 JVM 单元测试，覆盖成功结果、alias 精确匹配、优先级观察、诊断变体语义和异常隔离。测试使用 app 已生成的真实注册表，不依赖 UI mock。

Android instrumentation 不负责库功能断言：它只在后续有设备时验证页面可启动和结果列表可见。现有 package-name 模板测试应替换为这一 UI 冒烟检查，不能再作为库功能覆盖的依据。

Plugin TestKit 的 AAR、变体、重复类、缓存与 DSL 测试保持不变；运行时选择 API 和实例生命周期的核心规则仍应在 loader 模块增加专门单元测试，而不是由 demo 替代。

## 验收标准

- Debug 启动后，用户无需查看 Logcat 即可看见全部七个场景及总结果。
- alias、双接口与诊断的展示来自真实 `ServiceLoader` 调用。
- 一个场景异常时，页面仍展示其余场景。
- 新增测试先失败再通过，且原有插件与 app JVM 测试保持通过。
- Debug 和 Release APK 均可构建；Release 对诊断不可用不显示为失败。

## 自检

本设计没有未决占位项；运行时与构建期边界明确；不承诺在 app 页面中重复 TestKit 的构建期能力。优先维持现有 XML/View 技术栈，以减少兼容性与依赖变更。
